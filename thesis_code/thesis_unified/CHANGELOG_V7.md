# Version 7 — 2026-11-13

## Experiment controls and equal TOPSIS weights — 2026-11-18

New experiment distinguishes required dataset and conditional SSH/custom-weight inputs from optional defaults. Collapsible control groups expose packaging/transfer budgets, AE stopping tolerance and patience, seed, utility sampling, feature-selection cutoffs and protected columns, delivery scenarios, model reuse, simulation bandwidth, decision gates and SSH recovery. The API validates settings before starting a process and preserves explicit percentage units. A shared schema keeps optional UI and server defaults aligned. AE tolerance/patience are forwarded to the existing engine; its algorithm is unchanged.

Final TOPSIS defaults to equal weights. Custom weights are entered before launch, persisted, displayed and used for the primary view and sensitivity table. Named comparison profiles remain available. Phase 2's baseline still uses equal thirds. Added a separate one-slide LaTeX flowchart template in the main project.

## Aligned Phase 6 adaptive trials — 2026-11-18

Phase 6 now uses Phase 2's default maximum of 10 trials and first-successful-transfer cutoff of 10 seconds. Updated both main and bundled senders, the unified adapter (SSH and simulation), dashboard defaults/text, batch wrapper and standalone summary. Explicit trial-count overrides remain supported. Trial CSVs and integrated evidence preserve the first time, maximum, threshold and required count. Completeness and ranking checks validate the adaptive rule so legitimate slow one-trial deliveries qualify while incomplete fast benchmarks remain excluded. Retry behavior and PCA/AE/clinical algorithms are unchanged.

## Phase 2 adaptive transfer trials — 2026-11-18

Unified/dashboard Phase 2 now follows the main script's first-transfer rule: at most 10 seconds leads to 10 total trials by default; over 10 seconds leads to one. New `phase2_transfer_trials` and `phase2_repeat_threshold_seconds` settings separate this policy from Phase 6's `transfer_trials` (initially 3; subsequently aligned to 10 as documented above). Only clean successful transfer time controls the cutoff. Metadata records the policy and is included in Phase 2 checksum validation. Dashboard text distinguishes trials from failure-recovery attempts. Main-script packaging behavior and PCA/AE/clinical algorithms are unchanged.

## Remote directory naming — 2026-11-18

SSH upload attempts now use `<payload-filename>_unverified_<UTC-timestamp>_<unique-id>` directories. Only a successful checksum check of every uploaded file permits the atomic rename to `<payload-filename>_verified_<same-timestamp>_<same-id>`. Names are sanitized and bounded; retries and repeated trials get distinct paths. Network audit events record both planned paths, while successful trial CSVs record the published directory. Main Phase 2/6 scripts and unified/dashboard runs share this implementation. Existing remote folders are not migrated. See `README_SSH_RECOVERY.md` for discovery and interrupted-upload handling. PCA/AE, clinical-screen and decision algorithms are unchanged.

## Review findings and changes

1. **SSH eligibility:** v6 computed a remote-verification flag but did not use it to gate the ranking pools. Every v7 fidelity scenario, sensitivity table and recommendation now requires local integrity/recovery checks and, for SSH, an affirmative remote SHA-256 check plus finite integer trial counts meeting the requested count. Unverified SSH rows remain visible in the evidence CSV but are ineligible. Explicit `simulated_ideal` rows remain eligible only for provisional comparisons in separate pools. Unknown network modes are ineligible. Phase 2 TOPSIS also excludes unverified SSH rows and rejects mixed network pools.
2. **Delivery timing:** initial Phase 4 encoding and payload creation were omitted from the earlier effective-time proxy. Both delivery scenarios now appear as separate rows per package in evidence and rankings; all rank groups, sensitivity tables and recommendations include `delivery_scenario`.
3. **Artifact integrity:** Phase 3 checkpoints now include every selected CSV. Phase 4 checkpoints include PCA/AE payloads, lossless payloads and SHA-256 sidecars, in addition to metadata and comparison tables. Phase 6 retains archive, sidecar, report and trials checksums. A checkpoint without complete checksum coverage is rebuilt.
4. **Code and dependencies:** fingerprints include `run_thesis.py` and relative package paths, avoiding collisions between identically named files. Phase 2 TOPSIS depends on Phase 2 output; Phase 4 depends on selected input content and Phase 3; Phase 5 and each Phase 6 package depend on Phase 4 content and checkpoint generation. A rebuild at the same paths invalidates dependents even when the regenerated bytes happen to match. Independent checkpoints can still be reused. Existing v6 runs receive a new run ID.
5. **Empty results:** empty rankings retain a stable CSV schema. Empty pools and all-ineligible sensitivity cases render `none` and no recommendation. Empty network-trial exports also retain headers.
6. **Numeric validation:** costs must be finite and nonnegative; overlap must be in [0,1]; retention and violation percentages must be in [0,100]; R² must be finite and at most 1, with no lower bound. Invalid rows remain auditable but cannot be ranked. Direct TOPSIS calls reject invalid inputs. Vector normalization is scaled before squaring to handle large finite values. Simulation bandwidth must be finite and positive.
7. **Fallback:** `auto` with `fallback_simulated=false` now fails on preflight in the runner and both network adapters. Explicit `simulated` mode remains valid. Strict SSH continues to prohibit fallback. Phase 6 checks this before building a package.
8. **Expansion:** Phase 2 TOPSIS accepts negative size reduction as a valid benefit measurement when output files expand; times remain nonnegative and size reduction cannot exceed 100%. All-zero columns no longer cause division errors.
9. **Timestamped reports:** every successful invocation, including a checkpoint resume, publishes all six reports together in `results/YYYYMMDD_HHMMSS_microseconds_UTC_unique/`. Previous snapshots remain unchanged. `run_status.json` and the `RESULTS:` console line identify the completed snapshot. Publication uses an atomic directory rename after all copies succeed; failed copies do not leave partial published snapshots.

## Timing definitions

Let `B = end_to_end_seconds`, the existing Phase 6 proxy:

`B = package creation + local verification + transfer + remote verification (SSH only) + local unpack + local recovery`.

| Delivery scenario | TOPSIS effective delivery time |
|---|---|
| `existing_payload` | `B` — Phase 4 payload already exists; no fit, encoding or initial compression is charged |
| `fresh_data`, PCA/AE | `B + fit_seconds/model_reuse_count + encode_seconds + Phase4 packaging_seconds` |
| `fresh_data`, lossless | `B + Phase4 lossless packaging_seconds` |

Only fitting is amortized. Encoding and payload creation occur on every fresh-data delivery. Initial NPZ creation includes serialization/compression and its sidecar as measured by Phase 4. Phase 6 envelope creation and optional codec conversion/recompression remain charged in `B`; they are distinct operations in the current pipeline. CSV loading, preprocessing, feature selection and metric evaluation remain outside these scoped delivery proxies. `existing_payload` means an existing Phase 4 payload, not an already-built Phase 6 TAR archive.

The evidence table exposes `model_fit_seconds`, `initial_encode_seconds`, `initial_payload_creation_seconds`, `initial_preparation_seconds_charged`, `model_reuse_count_assumed` and `delivery_scenario`. Missing or invalid preparation components invalidate fresh-data timing instead of being replaced with zero. The manifest counts packages once, while the evidence CSV normally has two rows per package.

Receiver recovery is still timed locally. Simulated transfer remains an ideal bytes/bandwidth calculation, and neither scenario establishes clinical acceptance or actual remote ingestion performance.

## Algorithm preservation

The Phase 1, Phase 3 selection, Phase 4 PCA/AE and clinical-screen, and Phase 5 utility engines remain byte-for-byte unchanged from the reviewed project. The SSH recovery follow-up changes transport handling in the Phase 2 and Phase 6 engines; the standalone Phase 2 TOPSIS changes remain limited to input validation and robust normalization. No PCA fit/transform, AE architecture/training, reconstruction metric, clinical bound or clinical-screen denominator was changed.

## Validation

Run from `thesis_unified/` with the dependencies in `requirements.txt` installed:

```bash
python -m unittest discover -s tests -v
python tests/synthetic_pipeline_v7.py --output-dir /tmp/thesis-v7-smoke
```

The smoke output path must not already exist. The synthetic test runs all six real phases on 64 generated rows from 16 synthetic patients, using original and selected feature sets, PCA/AE k=2, all three lossless formats and all three NPZ codecs. A short AE iteration budget is intentional for this execution test; its result is not a model-quality benchmark. It checks 18 packages, both delivery scenarios, finite rankings, all six final reports and unchanged phase checkpoints on resume. SSH preflight calls raise immediately, and SSH/SCP executables are replaced by failing sentinels. No real patient data or SSH endpoint is used.

`tests/test_validation_v7.py` covers unverified/partial SSH, non-finite and out-of-range criteria, negative R², timing formulas, empty rankings/reports, artifact coverage, runner fingerprints, dependency propagation, disabled fallback and Phase 2 expansion. See `VALIDATION_V7.md` for the completed validation results.

## SSH recovery follow-up — 2026-11-15

Shared transport recovery now covers the root and unified Phase 2/6 senders: bounded transient retries, keepalives, process-group deadlines, remote archive and sidecar hash checks, and atomic publication of verified directories. Uncached preflight observes reconnections and outages. Audit records separate failed attempts and backoff from successful SCP timings. Strict SSH/fallback-disabled policies remain fail-closed. The dashboard can resume failed/stopped/interrupted jobs using their saved configuration and validated checkpoints. See [README_SSH_RECOVERY.md](README_SSH_RECOVERY.md) for method wording and limitations.
